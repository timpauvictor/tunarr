## 1. Goal and accepted scope

Create ordinary Tunarr TV channels from YouTube content, without keeping downloaded source videos. YouTube must be a first-class media source in the existing settings, library, programming selector, guide, and playback flows.

User decisions from this planning session:

- Include public/accessible unlisted playlists, creator-channel uploads, and individual finite recorded videos in V1.
- Import links directly from the existing channel programmer using the configured YouTube source. The programmer and library share the same server import operation and persistent catalogue; users do not have to visit the library first.
- Refresh the source library without automatically replacing or reordering existing channel programming. Use the existing programming editor for deliberate channel updates; no dedicated playlist-diff preview, synchronization wizard or new channel-update API is required. Automatic follow-playlist scheduling is deferred.
- When unwatched, a normal linear channel keeps advancing logically but does not fetch/transcode the video. On tune-in, play the scheduled video at its current scheduled offset.
- Match repository code style and architecture; do not create a parallel application or YouTube-only channel scheduler.

Recommended V1 boundaries, not additional user decisions:

- No Google sign-in, cookies, private/account-only content, paid content, DRM, running livestreams, premieres waiting to start, or YouTube search/recommendation browsing.
- Creator-channel input means its uploads collection, not subscriptions, every channel tab, or an ongoing live relay. Normalize handles/URLs to stable channel identity.
- No arbitrary five-minute minimum or silent exclusion of short finite videos. Eligibility depends on accessible, finite, positive-duration, supported seekable media.
- Metadata, thumbnails, extractor challenge cache, and bounded transient HLS/transcode segments are allowed. No full-video download, permanent video library, or scan-time media prefetch. Streaming necessarily transfers video bytes while watched; this is not zero-download in the network sense.
- A first-party YouTube embedded-player product would not satisfy normal Tunarr M3U/HDHomeRun/local-TV playback. Do not silently substitute one.

### Reliability and policy constraints

- yt-dlp's current YouTube guidance includes external JavaScript challenge solving. Official executables bundle EJS solver scripts but still need a supported JS runtime. Deno is recommended; Node >=22 is supported when explicitly enabled [S2]. Tunarr's development Node is not proof that its packaged production executable can serve as a general Node runtime.
- PO tokens are required for some client/format combinations; missing tokens can produce 403s or blocks. Requirements change. Do not hard-code one current client workaround, copy tokens from issue comments, or promise that Deno solves all anti-bot failures [S4].
- yt-dlp documents request-rate limits and account-ban risks when cookies are used. A flat listing may lack duration or other fields, so listing a large channel and hydrating every item at once is not free [S1, S3].
- Extracted URLs can require the same egress IP and HTTP context as resolution. Keep resolver and FFmpeg/worker on the same host/network path and preserve the selected input's required headers. Never send Google media URLs to TV clients [S3].
- SABR-only formats and contemporary 403 reports demonstrate that a public, browser-playable video is not necessarily a seekable FFmpeg input. A user report is evidence of a failure class, not a measured failure rate for our installation [S9].
- FFmpeg supports input seeking and HTTP range/reconnection options, but reconnecting to an expired signed URL is not URL renewal [S10]. Validate actual candidates and bound recovery.
- YouTube's terms restrict automated access and transmission/broadcasting except where authorized; its API policies also restrict audiovisual manipulation and redistribution [S11]. LAN-only use and avoiding full-file storage do not establish permission. This is a product/policy risk, not legal advice. The operator is responsible for appropriate rights/authorization before production use; do not advertise this as an official YouTube integration. This warning is not an upstream maintainer-approval gate for personal-fork development.

**Conclusion:** technically plausible as a maintained, best-effort source, not a guaranteed YouTube receiver. First prove public VOD extraction and seeking from the intended host. If it requires credentials, token-provider infrastructure, SABR support, or a relay service to be useful, stop and revise the scope rather than hiding those dependencies in the UI.

## 4. Proposed design

The direct flow is URL -> metadata adapter -> ordinary programs and ordered collections -> existing channel programming/clock -> playback-time resolution -> existing FFmpeg/ErsatzTV pipeline. YouTube supplies content, not a new scheduler, stream proxy or session framework. Two real contract changes are necessary: ordered collection occurrences and multiple playback inputs. Do not avoid the latter by limiting support to whichever combined formats happen to be available.

### 4.1 Data and ingestion

- Add `youtube` as a media source with a display name and a stable source UUID, no account credentials in V1. Its typed settings must not pretend to require a server URL or access token. Handle existing DB storage constraints explicitly in the migration.
- Give a YouTube source one catalogue library. Store canonical video IDs as source-scoped program identity and `other_video` content. Preserve repository canonical-ID/change-detection conventions; IDs must not depend on display names, playlist position, or signed URLs.
- Use existing external collections for user-added playlists, creator uploads, and a Saved Videos collection for individual imports. Collection origin/kind, canonical upstream identity, refresh state and source linkage must be persisted, not reconstructed from labels.
- Extend collection membership to ordered occurrences with a stable local entry ID, position and program reference. Recommended design: migrate the existing membership owner to support ordered entries while keeping current non-YouTube set-oriented repository methods backward-compatible. Preserve existing grouping memberships and avoid writing a second authoritative membership ledger. Freeze the exact migration/API shape during packet 2's collection compatibility trace; it is not a packet-0 prerequisite.
- A video can appear in several collections and several times in one playlist while referring to one program within the source. Preserve upstream entry identity when available. If extraction supplies only video IDs/positions, match repeated occurrences deterministically to retained local entry IDs; do not claim distinguishability that the upstream data does not provide.
- The collection view carries entry ID and program ID separately. Default playlist order is upstream order; repeated entries must not collapse through program-UUID keyed selection or pagination. Ordinary catalogue search remains program-oriented.
- Resolve playlist/channel listings with bounded pagination and metadata-only extraction. Hydrate missing finite durations inside the existing import job using bounded work; reuse stored metadata and deduplicate video IDs within that job. A missing duration is not zero and is not schedulable. No separate hydration service, durable hydration queue or background backfill loop in V1.
- Reuse existing job progress/cancellation and expose actionable partial/error state; do not invent persistent job infrastructure. Publish collection membership only after a complete successful enumeration; a cancellation, token loop, or timeout retains the last complete snapshot. Enumerate to completion or fail with an explicit configured safety-limit error, never silently truncate. Resumable import checkpoints are deferred unless an observed requirement justifies them.
- Refresh adds/removes/reorders collection occurrences but keeps existing programs/lineup references safe. A video removed from one playlist is not globally unavailable. Confirmed inaccessible/private/deleted content is distinguished from transient resolver failure. Never delete a program merely because one listing omitted it.
- Do not fabricate media-file paths, pixel formats, codecs, or scan-time media versions to satisfy the current fetcher. Branch to the YouTube playback resolver before the existing first-version requirement. Collect durable descriptive metadata at scan time and actual selected stream metadata at playback.
- Automatic refresh does not invoke YouTube duration-based lineup rewriting. Introduce a narrow reconciliation policy in `ReconcileProgramDurationsTask` that preserves YouTube schedule snapshots, including when a global reconciliation is triggered by another source's scan. Keep other sources' current behavior. Updated durations can be applied through a deliberate edit/save in the existing programming editor. Reuse its current behavior; no dedicated impact-preview workflow.

Owners: the YouTube metadata adapter and program minter/upsert/API converters, existing metadata/artwork storage and `ArtworkService`, the existing guide materialization flow and `services/XmlTvWriter.ts`. Reuse those owners, not a YouTube-only EPG generator.

| Description                           | Normal program summary/description for details and XMLTV `desc`; validate bounded plain text, not upstream HTML.                                                                                                                                      |

- Import/hydrate descriptive metadata once through the existing bounded job, then let library/programming/guide consumers read persisted data. Missing optional values remain unknown. A failed/incomplete metadata request preserves good saved data rather than replacing it with an empty program. Likes/views are not Omnirating or age classifications.
- Channel EPG start/stop times come from the saved Tunarr lineup and existing guide calculator. Playlist order is an import default, not another guide timeline. Mixed-source programming, shuffling, filler and saved slot boundaries keep their existing semantics. Descriptive refresh can update displayed metadata without rewriting channel timing (C5).
- Browsing and web-guide/XMLTV generation must not invoke yt-dlp, media probing or playback resolution. They may use the established bounded thumbnail-fetch/cache path; image requests are not video playback and must not expose signed media URLs. No playback work on hover or guide generation.
- Wire YouTube thumbnails explicitly into the normal artwork path. The inspected XMLTV fallback and `ArtworkService` source derivation currently recognize Plex/Jellyfin/Emby, so a new source is not automatically covered. Prefer stored artwork records backed by the normal endpoint; extend source derivation only if the selected ownership path needs it. Preserve safe image fetching, existing cache/refresh rules and unrelated-source behavior. Missing/failed artwork shows the existing placeholder or omits the XMLTV icon, not a broken promised URL or failed programme.
- In packet 1, independently assert the imported video's title, description, thumbnail and scheduled start/stop in the web guide and exported XMLTV. Check publication date when supplied, missing optional fields/artwork fallback and zero playback/extractor/probe calls during guide generation. Reuse the same first-video fixture and existing XMLTV/artwork assertions; no separate guide framework or broad EPG campaign.

### 4.2 Resolver and input contract

Use one injected YouTube adapter with separate operations for metadata/listing and playback resolution. It owns executable invocation, schema validation, rate limiting, cancellation, transient format selection and sanitized errors. Reuse the existing process utilities where they satisfy the contract; extend them only for concrete cancellation, output-limit or redaction needs. `ChildProcessHelper` currently logs argument arrays and has timeout support but not all required controls.

- Execute a pinned yt-dlp companion executable without a shell. Ignore ambient user configuration, disable uncontrolled plugins/remote component downloads, and do not accept arbitrary extractor arguments from the UI. Enable only the configured trusted JS runtime. Use metadata-only/simulation flags for scans; never a download destination.
- Validate supported YouTube hosts and URL forms; normalize to canonical video, playlist or creator identity before extraction. A watch URL containing both video and playlist parameters must ask which the user intends to import. Reject arbitrary websites, credentialed URLs, path/scheme injection and private-network inputs.
- Validate yt-dlp JSON with shared/internal Zod boundaries. Enforce timeouts, bounded output, queue cancellation and termination of owned descendants. A cancelled request cannot start a late FFmpeg process. Playback jobs take priority over bulk metadata hydration.
- Keep returned media inputs ephemeral and server-only. Select real seekable HTTP media formats supported by the current FFmpeg profile; handle combined and separate audio/video candidates. Prefer compatible SDR H.264/AAC within the channel quality ceiling when available, without pretending all videos supply them. Do not return DRM, SABR-only, or non-seekable candidates as playable.
- Restrict selected URL protocols/hosts to the supported YouTube media transport, reject private-address destinations, sanitize required headers, and constrain probing/redirects. V1 must not become an arbitrary HTTP/file reader. Packet 0 found that native FFmpeg/worker requests do not use Tunarr's guarded HTTP client. The user approved `stream/YouTubeMediaRelay.ts`: server-registered, session-owned inputs are forwarded through an authenticated loopback endpoint, with allowlisted HTTPS Google media hosts, guarded socket DNS, validated bounded redirects and headers, streaming backpressure and cancellation. Native consumers receive only relay inputs; signed upstream URLs stay in server memory. This is not an arbitrary-URL proxy, a separate deployment service, a media cache or a retry framework.
- Keep the same egress IP/context for resolution, bounded probe and media consumption. Use actual per-input metadata; probe a bounded amount while a stream or explicitly requested diagnostic is active when extraction metadata is insufficient.
- Represent resolved inputs as a stable-identity collection with explicit track-to-input bindings at `ProgramStreamResult`, rather than copying the PR's permanent `separateAudioSource` special slot. Existing sources supply one input. Only change real consumers needed by this contract; no generic provider framework.
- Wire input bindings to normal FFmpeg video/audio inputs and the ErsatzTV mapper. Seek both tracks to the same scheduled media offset; cap the stream to the slot's remaining time. Map per-input headers and real stream indices, not presumed `0:0` video plus audio from the same input. Do not hand-edit generated worker schemas.
- Single-input copy/remux keeps its current behavior. Split inputs must use a proven transcode path initially; never feed the existing single-input copy-all path and lose audio. Unsupported source/mode combinations need a visible capability error or explicit user-confirmed profile change, not a silent global downgrade.
- Resolve inputs for the owning playback attempt/session and discard them when that attempt ends. Reuse existing same-mode session sharing rather than adding a cross-request URL cache, shared promises or per-waiter cancellation machinery. Different sessions may resolve independently within the adapter's bounded process concurrency. Add broader coalescing only after measuring a real duplicate-work problem. Never persist resolved inputs or assume a fixed YouTube URL lifetime.

### 4.3 Clock, viewers and recovery

The normal linear channel is the clock. An explanatory example is `(now - channelStart) modulo lineupCycleDuration`, then the existing lineup offsets locate the program and its within-program offset. Use Tunarr's actual calculator, including filler, redirects and scheduling rules, rather than implementing this simplified formula again.

- Idle: metadata refresh may run; no YouTube playback resolver/probe loop, worker, FFmpeg media input, or full-stream heartbeat exists solely to advance the clock. Guide/XMLTV generation reads durable metadata only.
- Tune-in: reuse the requested session, calculate the current item/offset, resolve current media URLs, then start the existing pipeline. If resolution crosses a slot boundary, recalculate before starting; do not play stale programming. Align actual output timestamps with the selected schedule point using the existing session timeline.
- Multiple viewers of the same channel/session mode share the current media session. Existing incompatible output modes may require distinct sessions; no new cross-channel transcoder sharing is in scope.
- Last viewer: disconnect and HLS heartbeat expiry use the existing session cleanup model. This is bounded detection, not knowledge of the physical TV's power state. Current defaults include 60-second heartbeat staleness and a 15-second cleanup delay, plus sweep/shutdown behavior; derive the effective bound from the session configuration. Cancel queued resolution and terminate media work when cleanup takes effect. A new tune-in racing cleanup must not inherit a dead session or lose its replacement files.
- Allow existing bounded work-ahead/transcode buffers only while a viewer-driven session is active; no always-on playlist prefetch. Preserve current bounded transient segment handling and cleanup; verify it rather than claiming no files are written.
- On restart, derive normal-channel position from persisted channel start/lineup, not an in-memory counter. Preserve explicit existing on-demand pause semantics separately.
- On media 403/expiry or transient network failure, discard the failed URL and allow one fresh resolution in the owning playback attempt. Bound transport retries and use the existing session/error lifecycle for subsequent attempts; do not add a shared retry/cooldown service. Never retry in a tight loop or reuse an expired URL forever. A second failure yields an actionable error and the existing error/filler output for the remaining scheduled slot. Do not silently compress the schedule by skipping a failed item early.
- A shorter source fills its remaining slot through existing error/filler output; a longer source is cut at the saved slot boundary. Schedule refresh/repair is a deliberate user action. Distinguish missing dependency, unsupported format, inaccessible video, rate limit/bot challenge, temporary network error and expired input in health/diagnostics.

### 4.4 First-class UI and UX

**Primary flow:** configure YouTube once in Media Sources -> open the existing channel programmer -> Import YouTube links -> paste playlist/channel/video URLs -> resolve/import metadata and review eligible entries -> add to the current programming draft -> save normally -> guide/watch through the normal player or IPTV client.

**Alternative flow:** import through the source/library, then browse/select the same saved programs in the programmer. Both entry points use one server import operation, identity rules, progress/cancellation and catalogue. No separate programmer-only importer, temporary URL lineup item or automatic saved-channel mutation.

1. **Source setup.** Extend the existing Add source menu and MUI dialog patterns. Display YouTube name/icon, a short availability/terms notice, extractor/runtime health and a Test setup action. No fake server-address/token fields. Advanced executable settings stay in the established system/settings pattern, not a required wizard step.
2. **Import from the programmer.** Add an Import YouTube links action to the existing programming selector/editor, scoped to the selected configured YouTube source. If no source exists, offer the existing setup flow without losing the draft or pasted input. Accept a collection of URLs with detected kind and per-input validation. Reuse the same import form/action from the source/library instead of implementing a second parser, endpoint or metadata job. Show resolved title, creator, thumbnail, eligible/pending/unavailable counts, source identity, progress and expected order. A mixed video/playlist URL requires explicit intent. Once import completes, explicit Add to programming uses the existing append/selection actions: one video adds one occurrence, playlists expand in upstream order with repeated occurrences intact, and multiple URLs retain the user's input order. Creator uploads use the selected explicit ordering. Unknown-duration/unavailable entries are not silently scheduled; show exclusions and require confirmation for a partial eligible set. Distinguish repeated input from repeated playlist occurrences. Cancellation/retry retain input, and retrying metadata import does not duplicate catalogue programs or append the same import result twice. Preserve all existing draft edits and mixed-source items; only normal Save persists channel programming. Imported metadata remains available in the library even if the channel draft is discarded. Completion after navigation/closing the flow must not append to another or inactive draft; the imported library content remains available for later selection.
3. **Libraries/collections.** Extend the existing catalogue browser with collection views and source/creator attribution. Playlist views default to original order; creator uploads have an explicit chronological/reverse-chronological sort choice. Provide normal grid/list selection plus ordered Add all. Single videos live in Saved Videos and remain searchable with everything else. Paginate/virtualize with current components; selection survives reorder using occurrence identity.
4. **Refresh controls.** Reuse source/library refresh and job progress UX. Show last successful refresh, current job state, number added/removed/pending, failure reason and retry. State plainly: 'Refreshing updates this library, not existing channel programming.' Link to the existing programming editor for deliberate channel changes; do not add a diff preview, synchronization wizard or automatic playlist application.
5. **Channel integration.** Reuse programming tools, filler, watermark, channel icon/number, transcode profile and guide generation. Permit mixed local/Plex/etc. and YouTube programs. Explain that normal live/linear mode advances while unwatched; do not call it Tunarr's pause-on-idle mode. Surface split-input/direct-mode limitations before saving incompatible programming.
6. **Availability.** Cards/details show creator, duration, source link and non-destructive unavailable/pending badges. Metadata import success is not labeled 'playback verified'. Setup test checks dependencies/metadata by default; any media probe is an explicit diagnostic action with temporary network activity disclosed. Never autoplay or probe every card on hover/render.
7. **Style and accessibility.** Use existing MUI components/theme, responsive dialogs, labeled fields, keyboard flow, focus/error handling, Lingui `Trans`/`t`, generated TanStack Query calls and existing forms. Keep local drafts local and invalidate authoritative server queries after mutations. No new UI framework, duplicate global domain store, hand-authored generated API client, or raw upstream HTML.

When touching `AddMediaSourceButton`, prefer one selected-dialog discriminant over adding a fifth independent open/close boolean. This is a scoped simplification of the edited responsibility, not a rewrite of every source dialog.

### 4.5 Distribution and operations
